# LabRAG 구조

이 문서는 소스 코드를 따라가기 위한 지도다. 클래스 목록보다 요청이 이동하는 경계와 각 단계의 실패 처리에 초점을 맞춘다.

## 1. 요청 경계

[`labrag/server.py`](../labrag/server.py)는 OpenAI 호환 엔드포인트를 제공한다.

- `GET /v1/models`: Open WebUI에 노출할 모델 목록
- `POST /v1/chat/completions`: 일반 채팅과 스트리밍 응답
- `POST /search`: 라우팅과 검색 결과를 확인하는 진단 엔드포인트
- `GET /health`: 모델·Qdrant·Drive 연결 상태

Open WebUI는 대화 제목이나 후속 질문을 만들기 위한 내부 요청도 같은 API로 보낸다. 라우터는 이 요청을 사용자 질문과 구분해 Drive나 웹 검색을 호출하지 않는다.

## 2. 질문 해석과 라우팅

[`labrag/intent.py`](../labrag/intent.py)는 기간, 출처, 사람, 채널, 출력 형식 같은 구조화된 의도를 꺼낸다. [`labrag/router.py`](../labrag/router.py)는 이를 규칙과 함께 사용해 경로를 고른다.

우선순위가 필요한 이유는 한 표현이 여러 뜻을 가질 수 있기 때문이다. 예를 들어 “웹 크롤러 코드 찾아줘”의 `웹`은 출처가 아니라 주제이며, `찾아줘`도 파일 위치 요청일 수도 있고 내용 검색 요청일 수도 있다.

대략적인 판정 순서는 다음과 같다.

1. Open WebUI 내부 작업 요청인지 확인
2. 사용자가 강제로 지정한 모드 확인
3. Drive와 Slack을 함께 지정했는지 확인
4. 명확한 파일 위치 표현 확인
5. 내부 자료와 웹의 복합 요청 확인
6. 웹 출처만 지정한 요청 확인
7. 일반 대화와 내부 업무 힌트 확인
8. 애매하면 내부 인덱스를 짧게 조회

라우터는 답변을 만들지 않는다. `RouteDecision`에 모드와 판정 이유만 담아 서버로 돌려준다.

## 3. 내부 검색

[`labrag/rag.py`](../labrag/rag.py)의 `retrieve()`가 내부 검색을 조정한다.

### 후보 수집

- Qdrant dense 검색
- 파일명·경로를 사용하는 manifest 검색
- 정해진 업무 개념을 파일과 연결하는 canonical record
- 기간·채널이 명확할 때의 메타데이터 검색
- Slack 상위 스레드와 하위 조각 검색

각 검색기는 서로 다른 실패 형태를 보완한다. 본문이 숫자뿐인 파일은 의미 검색에 약하지만 경로 검색으로 찾을 수 있고, 채널의 최신 업무는 메타데이터 정렬이 의미 유사도보다 중요할 수 있다.

### 후보 정리

후보는 파일·스레드 ID로 합치고 리랭커에 전달한다. 리랭커의 절대 점수는 질문과 문서 형식에 따라 범위가 크게 달라질 수 있어 순위 선택에만 사용한다.

Drive와 Slack을 함께 요청한 경우 한쪽 결과가 높은 점수로 슬롯을 모두 차지하지 않도록 각 출처의 근거를 최소 한 건 보존한다. 채널 참여·탈퇴 같은 Slack 시스템 이벤트는 리랭킹 전에 제거한다.

### 문맥 확장

상위 조각 하나만으로 문장이 끊기거나 담당자 정보가 빠질 수 있다. 기본 설정은 최상위 결과에 한해 앞뒤 조각을 붙인다. 모든 결과를 확장하지 않는 이유는 프롬프트 길이와 중복 근거가 빠르게 늘기 때문이다.

## 4. 파일 위치 검색

[`labrag/location.py`](../labrag/location.py)는 인덱스의 파일명·경로 후보를 만들고, [`labrag/drive_live.py`](../labrag/drive_live.py)는 Drive API에서 현재 파일을 찾는다. [`labrag/location_merge.py`](../labrag/location_merge.py)는 파일 ID를 기준으로 두 결과를 합친다.

Drive 실시간 검색 결과는 바로 신뢰하지 않는다. 부모 폴더를 따라가 지정된 루트 아래에 있는지 확인한 뒤에만 답변 후보로 사용한다. API가 시간 안에 응답하지 않거나 인증을 갱신하지 못하면 인덱스 결과만 반환한다.

## 5. 웹 검색

[`labrag/web_search.py`](../labrag/web_search.py)는 Tavily 응답을 내부 `WebHit` 형식으로 바꾼다. 웹 검색 실패는 내부 RAG 실패와 구분해 메모로 남기고, 내부 근거가 있으면 그 결과만으로 답변을 계속 만든다.

웹 결과는 내부 문서와 같은 출처처럼 섞지 않는다. 복합 모드 프롬프트는 “내부 자료”, “웹에서 확인한 내용”, “종합” 섹션을 따로 요구한다.

## 6. 인덱싱

[`scripts/index.py`](../scripts/index.py)는 Drive 범위를 순회하고 변경된 파일만 처리한다.

```text
Drive 목록
  -> 파일 유형 판정
  -> 다운로드 또는 Google 문서 내보내기
  -> 구조 파싱
  -> 조각 생성
  -> 임베딩
  -> Qdrant upsert
  -> manifest 상태 기록
```

manifest는 성공한 파일뿐 아니라 파싱 실패와 OCR 필요 상태도 기록한다. 본문을 검색할 수 없는 파일이라도 파일명과 위치는 안내할 수 있기 때문이다.

## 7. Slack 색인

[`scripts/index_slack.py`](../scripts/index_slack.py)는 새 메시지를 수집하고 스레드 조각을 저장한다. [`scripts/build_slack_context.py`](../scripts/build_slack_context.py)는 긴 대화를 검색할 때 필요한 짧은 맥락을 만든다. [`scripts/index_slack_parent.py`](../scripts/index_slack_parent.py)는 스레드 전체를 상위 검색 단위로 저장한다.

상위 스레드는 넓은 주제를 찾고 하위 조각은 정확한 문장을 인용하는 데 사용한다. 답변 출처는 항상 실제 Slack 메시지 링크를 가리킨다.

## 8. 주간 최신화

[`labrag/refresh.py`](../labrag/refresh.py)는 각 갱신 단계를 독립된 `RefreshStep`으로 실행하고, 성공·실패·실행 시간을 `RefreshReport`에 모은다. 한 단계가 실패해도 나머지 진단 단계를 실행해 어느 경계에서 문제가 생겼는지 남긴다.

자식 프로세스에는 저장소 루트를 `PYTHONPATH`로 전달한다. `scripts/` 아래 파일을 직접 실행하면 Python의 import 기준점이 그 디렉터리가 되어 `labrag` 패키지를 찾지 못할 수 있기 때문이다.

systemd timer 예제는 매주 월요일 04:00에 같은 진입점을 실행한다. 이 과정은 검색 인덱스를 갱신하며 모델 가중치를 학습하지 않는다.

## 9. 실패 처리 원칙

- Drive 실시간 검색이 늦으면 로컬 인덱스 결과로 돌아간다.
- Slack 컬렉션이 없으면 Slack 검색만 비활성화한다.
- 웹 검색 오류는 내부 답변을 막지 않는다.
- 근거가 없으면 내부 자료를 봤다고 표현하지 않는다.
- 원시 인증 오류나 토큰 문자열을 사용자 응답에 포함하지 않는다.
- 검색 범위가 채널이나 출처로 좁혀졌으면 그 사실을 메모로 알린다.

## 10. 공개 저장소의 경계

공개본은 코드 경계를 보여 주기 위해 운영 저장소에서 선별한 파일이다. 실제 코퍼스에 맞춘 평가 데이터와 배포별 모델 경로는 없다. 예제 설정으로 구조를 확인할 수 있지만 검색 품질은 각 조직의 문서 구성, 임베딩 모델, 리랭커와 평가 질문에 따라 다시 측정해야 한다.
